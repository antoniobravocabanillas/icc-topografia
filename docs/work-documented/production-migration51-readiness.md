## Blocking findings

**B1 — Supabase staging authority is not a Prisma Postgres production operator.** `scripts/apply-s18-staging-migration.mjs:12-35` pins a Supabase project, host/user/database and CA; `scripts/prepare-s18-lifecycle-staging-migration.mjs:14-21,59-68,96-108,143-151` requires Supabase grantors, `postgres`, staging roles and ledger 50. S17/disclosure similarly assume 48/49 (`scripts/prepare-s17-staging-migration.mjs:99-102`; `scripts/prepare-s17-disclosure-staging-migration.mjs:86-89`). Do not change only the hostname/count or manufacture Supabase roles in production. Production role names, membership, object ownership, engine and permitted DDL are unverified here. Capture the real boundary and design a provider-specific wrapper. `db.prisma.io` alone is not a unique database identity.

Raw migrations do not supply the staging ACL overlay: selection revokes PUBLIC but not named/inherited grants; publication/invitation/evaluator wrappers depend on default runtime grants (`scripts/prepare-publication-staging-migration.mjs:45-52`; `scripts/prepare-s22-staging-migration.ts:71-86`). S17/disclosure/S18 functions execute as invoker, so required table reads/row locks and function permissions must work under the **actual runtime**, without owner/migrator bypass. Verify private schema access, new-table/function/default ACLs, membership and denial of runtime DDL/ledger writes. UPDATE immutability is not sufficient retention enforcement: the disclosure staging overlay even grants DELETE (`scripts/prepare-s17-disclosure-staging-migration.mjs:166-169`). Derive production privileges explicitly; do not copy that grant as an audit-history guarantee.

**B2 — Additive schema does not establish compatibility with the serving commit.** Provenance requires SERIALIZABLE before testing whether a binding exists: proposal payload updates (`prisma/migrations/20261120000100_closure_accepted_proposal_provenance/migration.sql:79-95`), acceptance updates/deletes (`:98-119`), closure reparenting (`:123-138`) and collaboration identity/party changes (`:140-157`). Thus unbound legacy operations can fail too. S18 makes document identity/storage immutable and blocks retained-history deletion (`prisma/migrations/20261120000300_professional_document_lifecycle/migration.sql:104-145`). Run the **exact serving commit and candidate** on the restored/migrated clone. Until that passes, migration-before-deploy and application-only rollback are unproven; require a fenced maintenance transition. No old application source was audited in this sidecar.

**B3 — Existing backup/rehearsal utilities do not cover this production baseline.** `scripts/prepare-attention-production-backup.mjs:13,23,35-37` pins a different served commit and requires followup to be absent. Its dump excludes ownership/ACLs (`:46`); its manifest ledger is captured before the dump in a separate transaction (`:32-46`). `scripts/restore-attention-production-local.mjs:45-77` checks an applied count and rehearses only followup. S18 restoration pins the staging site/project and ledger 50 (`scripts/rehearse-s18-staging-local.mjs:66-75,250-255`), reconstructs staging roles, and explicitly disclaims production readiness (`:458-470`). None is a substitute for a fresh production-derived 44 → 51 restore. Do not run these unchanged against production or treat archive readability as restoration proof.

**B4 — Atomicity, lock budget and recovery remain unmeasured.** First three raw migrations have no outer BEGIN/COMMIT; the other four do. Publication/selection wrappers require an external transaction (`scripts/prepare-publication-staging-migration.mjs:17-22`; `scripts/prepare-selection-access-staging-migration.mjs:17-22`). Blind concatenation or wrapping embedded COMMITs does not yield seven-migration atomicity. The S18 reference deliberately unwraps its boundary, locks the ledger and every existing table, materializes full row multisets, then writes the ledger in the same transaction (`scripts/prepare-s18-lifecycle-staging-migration.mjs:84-149`). This blocks writers and may consume substantial time/temp space on production. Existing-table ordinary indexes, evaluator type conversion, FK/check validation and trigger installation require a measured lock/WAL/disk budget. Only provenance has raw SQL timeouts; extending timeouts or changing the transaction plan invalidates the prior rehearsal.
